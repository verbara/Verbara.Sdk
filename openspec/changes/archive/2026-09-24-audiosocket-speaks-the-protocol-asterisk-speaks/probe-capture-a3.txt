Hangup — NOT CAPTURED, and this is the finding
----------------------------------------------
Two runs ended the call two different ways:
  - `channel request hangup all` from the CLI, and
  - the far leg reaching Hangup() in the dialplan on its own.
Both ended the same way: the listener printed "peer closed the connection" with ZERO trailing bytes
after the last complete frame. Asterisk 22.9.0's app_audiosocket closes the TCP connection; it does
not send a 0x00 hangup frame in the Asterisk -> server direction.

No hangup entry was written into the fixture. A hand-written one would be a guess dressed as a
capture, which is the closed loop this change exists to break. 0x00 stays the hangup type in the
OUTBOUND direction (the SDK sends it to ask Asterisk to hang up) on the strength of the type table,
not of a measurement, and it is recorded that way.


What this adds to the measurement the change rests on
-----------------------------------------------------
  Uuid   = 0x01   confirmed a second time, and now with a UUID that pins RFC 4122 byte order
  Audio  = 0x10   MEASURED, not inferred from AudioSlin12 = 0x11
  Dtmf   = 0x03   MEASURED; neither enum has a member for it today
  Hangup = 0x00   still unmeasured inbound; Asterisk closes the socket instead
  header = 1 byte type + 2 bytes big-endian length, on 1,411 frames across the runs, 0 trailing bytes
